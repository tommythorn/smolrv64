# Handoff — in-order core, 2026-08-18

## Milestone reached

**Geekbench 5 runs end to end.** 25.4 h, both passes (single- and multi-core), all 20
workloads, zero validation failures.

    https://browser.geekbench.com/v5/cpu/compare/24546964
    model: SmolRV64 inorder-nospan 53bb94bf @ 111 MHz     (Integer Score 0 — room to grow)

Build: branch `inorder-nospan` @ `53bb94bf`, PROBE_CLK_DIV=3 (111 MHz), Ubuntu 25.04 over
NFS. AES-XTS passed in both passes; Camera passed. Those two were the only workloads that
ever failed on this core.

## The bug: cause established, mechanism NOT

**Cause: the D-cache line-crossing (span) path.** Established by A→B→A on hardware:

| build | span path | AES-XTS | Camera |
|---|---|---|---|
| `53bb94bf` nospan | unreachable | pass (x4) | pass (x2) |
| `76db164c` control | intact | **fail** (x2) | — |

Same board, same day, same kernel and workload. Independently, the RTL-vs-simmerv cosim
caught the corruption itself after 17.0 G retirements:

    seq=17002543644  pc=0x152dbe  lb a1,12(s0)   DUT 0x00  vs  REF 0x25   (VA 0x3f7a3adffc)

`0xffc & 63 == 60` puts the corrupted byte in the line's **last 8 bytes** — exactly the
chunk a span low half writes. dc95e905 reports the same fingerprint from the OoO hunt:
"always a line's last 8 bytes (where a span's low half lands), one word, and no store to
the address."

**Mechanism: still unknown.** Four candidates ruled out —

1. c7f06b39 MSHR install stealing line0 slot — *impossible here, this fork has no MSHR*
2. line1 own fill stealing line0 slot — *impossible: line0/line1 differ by one index; the
   only aliasing case is a 64 KB wrap, which is also a page crossing and is trapped*
3. dc95e905 NC/WT push carrying the wrong line — *push-integrity check armed through a
   full hardware reproduction, silent*
4. a PTW fill landing inside the span window — *directed test with paging, 256 distinct L0
   tables, sfence.vma and CBO churn: clean*

## The fix that works today

The LSU aligns every DRAM access to its containing 8-byte word and does byte extraction
(loads) / placement (stores) itself, splitting a straddling operand into two accesses. The
cache therefore never sees a span. MMIO keeps its exact address (devices decode by low
address bits). Cost measured: kernel unaligned probe 5.85x -> 4.14x.

## Timing

111.7 -> 111.9 MHz across three fixes. The delta is noise; **the diagnosis is the result**:
the frontend (predictor arrays included) is combinationally tied to *does M complete this
cycle* via the stall-the-whole-pipe handshake (`m_addr -> lsu_done -> m_advance -> accept`).
178 paths sit within 0.5 ns of critical, all feeding one cone, so point fixes buy ~0.05 ns
each. The structural move is an elastic/skid buffer so `accept` reads registered state.

BUFGCE_DIV divides ui_clk (333.333 MHz) by an integer, so reachable clocks are
66.7 / 83.3 / 111.1 / 166.7 / 333.3 MHz. **Every improvement below a whole step is worth
nothing.** An MMCM for probe_clk would make the frequency continuous and is worth doing
before more timing work.

`inorder-newcache` should *help* timing: the old D$ hit path was a two-phase lookup plus a
byte-rotated window muxed across even/odd banks; the new one is a tag compare and an 8:1
word mux. That is the path currently feeding `lsu_done`.

## Test infrastructure — three real gaps

1. **The 240 riscv-tests do not exercise the cache at all** (`tb_ino_riscv.v` is flat
   memory). Every "240/240" after a cache change said nothing about the cache.
2. **`tb_ino_linux.v` has no virtio** — MMIO addressing is untestable in simulation. Three
   hardware round trips this session traced to this. `src/tb_cosim_linux.v` has the
   `virtio_mmio`/`virtio_blk` subsystem to port (~100 lines).
3. **`ILA_PARITY` was dead silicon on this core** — `probe_par_err` was tied to `2'd0`
   under INO_CORE, so hours of "no trigger" meant nothing. Now driven by the
   push-integrity check; keep it wired to something real.

## Open question: adapt this to the sharded OoO core?

Probably yes, and the case is *stronger* there:

* The OoO core shares the `cache.v` lineage and showed the **same corruption fingerprint**
  (that is why WTCHK/ILA_PARITY exist at all). c7f06b39 mechanism — an MSHR install
  reallocating a slot captured a phase earlier — **can** occur there, because it has an
  MSHR. So the class is live on that core in a way it is not here.
* Making the OoO LSU issue only aligned accesses removes the span path there too, and
  would let the same simple cache be used.
* Harder than here: the OoO LSU is non-blocking with several ops in flight, so splitting
  one op into two accesses means tracking two responses per op rather than sequencing two
  states. The existing load queue/scheduler is the place to do it.
* Cost is the same shape (two accesses per straddler) and matters more for a throughput
  core — but AES-XTS did 19.7 G memory accesses with **zero** misaligned, so the feature
  may be worth far less than it costs.

## Gotchas that cost real time

* **Check what you built.** Two builds were silently wrong: `make bit` with no flags builds
  the *OoO* core at 66.7 MHz, and a failed branch switch built the buggy new cache. The
  monitor `rtl=<commit>` banner is the cheap guard.
* **Never use pattern-based process kills over ssh.** `pkill -f`/`pgrep -f` match the ssh
  command line and kill the session (happened 4x). Use `ps`, then kill explicit PIDs.
* **Never filter a long run output through a whitelist.** A grep for
  `Running|validation|Score|Geekbench` discarded the result URL of a 25-hour run
  (`browser.geekbench.com` is lowercase). `gb5run.sh` now tees raw output to
  `/var/tmp/gb5raw.log`. The preview build has no `--save`, so stdout is the only copy.
* **Sims run on m5, never coffee** (coffee is half speed and owns Vivado + the board).
* `grep -c` prints `0` *and* exits 1; `$(grep -c ... || echo 0)` yields `0\n0`.
* Baseline every log pattern before watching for it — `screenlog.0` is cumulative and
  produced two false "failure detected" alarms from stale text.
* macOS has no `setsid`; git refuses a symlink at a submodule path (worktrees need
  `third_party/cvfpu` symlinked, and removed again before `git reset`).
* Heredocs with apostrophes inside an ssh double-quoted command break; write locally and
  scp instead.

## Suggested next steps

1. Port virtio into `tb_ino_linux.v` — closes the biggest validation blind spot.
2. Finish `inorder-newcache` (fix `scan` width `[IDXB:0]`->`[FW:0]`; find the read bug at
   retire #634126); the cosim catches its defects in ~2 min.
3. MMCM for `probe_clk`, then the skid buffer — in that order, so timing gains are visible.
4. Decide whether to chase the mechanism or let the rewrite make it unreachable.
