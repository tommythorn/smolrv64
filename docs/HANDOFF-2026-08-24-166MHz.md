## What closed it

Three families, and the two that mattered were both a late SELECT bolted to an array — not
deep logic. Full reasoning is in the two commits; the short version:

**`f0dedef2` — predictor arrays to block RAM (33 endpoints, −0.217).** The worst path was
the whole fetch loop, 6.462 ns of a 6.245 ns budget. `ft_npc` arrives at 4.35 ns, which
*fits*; the other 2.11 ns was array shape. `ycorr_v[yidx(npc,ghr)]` was a 1024:1 LUT/MUXF
tree (1.051 ns) and the index drove 161 distributed-RAM address pins (0.546 ns of route).
Folding valid into the entry and forcing `ram_style="block"` gives one RAMB18 and one
RAMB36 and ends the path at a BRAM address pin. The write-forward had to move *past* the
read register to allow that — a BRAM's read register is inside the primitive, so the
output-side forward mux was itself what kept the array in LUTs.

**`f0dedef2` — device decode off the load return (57 endpoints, −0.215).** `ino_soc_top`
still selected `raw_rdata` by re-decoding `dmem_raddr`: 1.27 ns of masked 64-bit compares
ahead of the mux, then load alignment and the X-stage ALU into `m_result`. Its two siblings
(`dmem_wready`, `raw_rvalid`) had already been collapsed onto the response valids. Third
instance, same module — now rule B5.

**`b1494b26` — ahead prediction.** The predictor's array read is addressed from registers
only (`apc`), enabled by `fire | rollback | reset`. Worth only 30 ps today, because after
the array fix the predictor cone was no longer binding — its value is that the fetch loop
stops constraining Fmax at all. Costs **0.13%** of retires (9,171,260 vs 9,182,948 over 40M
cosim cycles). See D4 for why the 2026-08-23 attempt hung and this one does not: it is the
same shortcut with the entry stamped by the address actually indexed.

## What the limiter is now

The predictor is **gone from the top paths entirely**. On the `Explore` build the tightest
core path is `m_addr → redirect_target_q` (5.921 ns, 26 levels); on `AltSpreadLogic_medium`
it is `u_fetch/pc_q[59] → fe/q_dat` — PC → iMMU translate → I$ data → the F/X queue's
LUTRAM write data, i.e. the raw fetch cloud with nothing hanging off the end of it.

There is no cheap RTL win left at 166. What remains:

1. **`u_fpu` internal (32 endpoints, −0.162 in the pre-fix build)** — `mid_pipe_sum_q →
   out_pipe_result_q` inside `fpnew_fma_multi`, the normalise+round back-end. Vivado has
   already retimed it in both directions (`_fret`×5 / `_bret` on the endpoints), so it is as
   balanced as the available registers allow. `PipeConfig: DISTRIBUTED` gives
   `NUM_OUT_REGS = NumPipeRegs/3`, so splitting that block needs `PIPE_REGS` 4 → **6**, not
   5: +2 cycles of FP latency, on 28.5% of GB5 cycles. Do not spend it unless a build
   demands it — it did not fail in either of these two.
2. **333.33 MHz is a re-pipelining, not a tuning exercise -- now measured, not asserted.**
   Built at `PROBE_CLK_DIV8=24` so Vivado optimised against 3.000 ns with full effort:
   **WNS -2.492, TNS -39,964 ns, 39,389 of 152,456 endpoints failing (26%).** The worst path
   came out at ~5.49 ns versus ~5.83 ns for the same RTL built for 6 ns, so maximum tool
   effort is worth about **340 ps**. The path is logic-depth-bound, not effort-bound; do not
   go looking for a directive or a constraint that closes this.

   The failing families are the whole machine, and the flatness is the finding -- there is
   no outlier to fix:

   | endpoints | worst | family |
   |---|---|---|
   | 776 | -2.430 | `u_dcache/cur_line -> valm` (fill path) |
   | 717 | -2.376 | `m_addr -> u_csr` |
   | 665 | -2.431 | `fb_va -> fe` (fetch buffer into the frontend) |
   | 165 | -2.436 | `fe -> fe` (the fetch loop) |
   | 129 | -2.344 | `u_fpu` internal (cvfpu FMA back-end) |
   | 104 | -2.348 | `fb_va -> u_icache/banks` |
   | 97 | -2.437 | `fe -> m_result` |
   | 90 / 64 | -2.43 | `m_st_data -> m_result` / `-> m_target` |
   | 60 | -2.419 | `m_addr -> redirect_target_q` |

   Every stage needs splitting: F (iMMU + I$ + aligner), X->M (ALU + bypass), M (load align,
   CSR, trap target), the D$ fill path, and the FPU. And there is no intermediate rung to
   aim at -- probe_clk is ui_clk/N for integer N, so 166.67 -> 333.33 is the next step and
   it is a factor of two.

3. **There is no thermal or voltage lever, and this was tested rather than assumed.** The
   board is actively cooled; SYSMON reads **32.9 C** on the die under sustained load with
   **VCCINT 0.853 V**. Vivado's defaults for this part are already `Junction Temp = 25.8 C`
   and `Vccint = 0.850 V` -- i.e. it is not being pessimistic about heat, it is assuming a
   die *cooler* than the one we have. Re-timing the routed checkpoint across junction
   temperatures 35..85 C and VCCINT 0.840..0.850 V moved WNS by **exactly zero** (-2.437 at
   every point): on UltraScale+, `set_operating_conditions` feeds POWER analysis only, and
   setup signoff comes from the speed file's fixed slow corner, whose VCCINT range
   (0.825/0.850/0.875) already contains the rail. The fansink keeps the part inside the
   envelope the signoff already assumes; it cannot buy Fmax. `opcond_sweep.tcl` reruns this
   in about a minute on any routed checkpoint. The only genuine "less conservative" lever
   is a -3 part, which is silicon.
3. **The cache floorplan** (`u_dcache`/`u_icache` pblock) is still the cheapest untried
   lever, constraints only. 64 KB may have made it unnecessary — it is not failing now.
